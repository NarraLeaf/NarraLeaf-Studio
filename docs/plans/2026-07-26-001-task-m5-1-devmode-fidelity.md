## WI-1 跳转落点精度（先诊断，再修）

**症状**：在 Dev Mode 时间线点某一行，游戏没有停在那一行。A3 的执行者跑了对照组——不带 `goto` 的普通前向跳转**同样落短**，所以这不是 `goto` 引入的，是热跳/冷跳本身的精度问题。

**先做诊断，把结论写进报告**，再动手。三个我认为最可能的方向（不要预设结论，以代码为准）：

1. **`until:{actionId}` 的语义是"目标执行前停"**（引擎 M4 的设计，见 `docs/plans/reports/2026-07-23-M4-engine-report.md`）。若如此，快进结束时**目标行还没执行**，画面停在上一行——从作者视角就是"落短了一行"。这可能是主因，且它是"按设计正确、按体验错误"的典型。
2. **一个块可能编译成多个 action**，`actionIdBindings` 反查时选了哪一个（首个？最后一个？）会决定停在块的哪个边界。
3. **冷跳路径**（`startBlockId` 预置舞台后向前播）与热跳可能各有一套落点定义，两者不一致。

**要达到的语义（这是本卡的验收口径）**：作者点第 N 行 → 游戏**显示第 N 行的结果**。对话行意味着那句台词已经出现在对话框里；演出行意味着那个演出已经落终态。冷跳与热跳必须**给出同一个落点**。

若正确修法需要引擎侧配合（例如 `until` 需要一个"目标执行后停"的变体），**停机报告**——不要在 Studio 侧用"多走一步"之类的补偿去猜引擎的边界语义，那会在 skip/menu 等边界上产生新的不一致。

## WI-2 相机姿态进舞台快照

**症状**：行级"从此处播放"时镜头总是中性的。若该行之前有 `/camera zoom 2`，真实播放到那里镜头是推近的，Dev Mode 里却不是。

**这条已有明确判据**（A2 复核的结论，不必重新论证）：舞台快照**本来就模拟**位姿，甚至连 displayable 的 `darkness` 都模拟（`storyStageSnapshot.ts` 的 `StageSnapshotEffects`），而启动编译是**从快照喂进去**的（`storyCompiler.ts` 的 `launch: {targetBlockId, snapshot}`）。相机姿态是**已被模拟之物的结构性兄弟**，不是 video/audio 那种从不进快照的东西。所以它该进。

- 在快照里累积相机姿态（pan/zoom/rotate/darken 的最终值），启动编译时预置。数值仍要**钳制**（照 `Math.min(1, Math.max(0, x))` 的仓内 idiom，与 A2 的编译侧一致）。
- **一个必须明确面对的边界**：相机是 story 级单例、姿态**跨场景保留**，而舞台快照是按场景算的。所以"在上一个场景里推近、jump 过来"这种姿态**静态不可复现**。v1 的口径：**在启动场景内累积**，跨场景部分不复现——但要在报告里写清这条限制，并说明它对作者的可见后果。不要为此去回溯 jump 链（那是可达性问题，静态不可靠——总计划 §3.9 同族）。
- 顺带确认 A3 给 `vfx` 加的"未预览"诊断在这条路径上仍然成立（不要因为改了 `applyAction` 的分支结构而丢掉它）。

## 明确不做

改引擎（WI-1 若需引擎配合就停机报告）；相机的 opacity/scale/filter/mask 等其余 Displayable 方法（A2 的 §11 开放项，另议）；把 video/audio 也塞进快照（它们从不进快照是有意的）。

## 验证与停机

`yarn lint` 全绿；vitest 新失败 0（win32 基线 `src/shared/utils/path.test.ts` 3 条）。快照侧要有单测：`/camera zoom` 后取快照，姿态被记录且被钳制；`/rename` 不覆写外观（A3 刚修的那条，别回退）。

**真机是本卡的硬验收**（这是保真度卡，只有真机能证明）：①点时间线上若干行（对话行、演出行、容器内的行），确认每次都停在**该行的结果**上，冷跳热跳一致；②在 `/camera zoom 2` 之后的某行做行级启动，确认镜头是推近的；③在前一个场景推近、jump 后启动，确认行为符合你在报告里声明的口径。截图/短录屏存 `docs/plans/reports/assets/`。

停机：WI-1 需要引擎语义配合；相机姿态入快照会破坏既有快照的序列化兼容（报告实例）；单个 WI 规模超预估一倍。
