## 2. The shared projection's public interface

`@/lib/story/storyRowProjection` — React-free, no workspace service, unit-tested.

```ts
type StoryRowCharacter = { name: string; color?: string };

type StoryRowLookups = {
    character: (characterId: string) => StoryRowCharacter | null;   // required
    assetName?: (assetId: string) => string | null;                 // omit = ids print as ids
    scene?: StoryScene;                                             // variable / layer / displayable refs
    scenes?: Record<StorySceneId, StoryScene>;                      // jump targets, cross-scene names
    document?: StoryDocument;                                       // names the inline chips
};

type StoryRowFragment = { kind: "text"; text: string } | { kind: "quick"; param: QuickParam };

type StoryRowProjection = {
    sentence: string;            // the row, minus the dialogue nametag
    speaker: StoryRowCharacter | null;
    barColor: string | null;     // the editor's left-edge hue; null on prose rows
    containerPill: string | null;
};

projectStoryRow(block, lookups): StoryRowProjection      // one pass, everything a row surface needs
storyRowSentence(block, lookups): string
storyRowFragments(block, lookups, label?): StoryRowFragment[]      // the whole row
storyActionRowFragments(block, lookups, label?): StoryRowFragment[] // just the action path (what `blockOverview` is now)
storyRowSpeaker(block, lookups): StoryRowCharacter | null
storyRowAccentColor(block): string                        // always a hue (danger for `invalid`)
storyRowBarColor(block): string | null                    // null on the rows the editor bars-less
storyBlockBadge(block): { id; labelKey; group }           // the badge chain, icons excluded
describeStoryBlock(block, lookups): string                // the base sentence
getStoryContainerHeaderInfo(block) / storyContainerChain(scene, blockId)
getStoryTextSegment / getStoryEmptyTextPlaceholder / getStorySceneName / storyCharacterName
storyTextSegmentPlain(segment, lookups): string           // rich runs → what the chips read as
```

The editor keeps its old names as adapters, so no call site outside these files changed:
`describeBlock(block, characters, …)`, `describeBlockSubject(…, resolveAssetName, …)`,
`getBlockBadgeInfo`, `getContainerHeaderInfo`, `getTextSegment`, `getSceneName`,
`getEmptyTextPlaceholder`, `blockOverview` — all still exported from where they were.

**Row dispatch** mirrors the editor's renderer, because that was the actual finding of §0.2 — the
editor's sentence is not `describeBlock`:

1. container → its pill (+ `N times` for a repeat), then
2. a text segment → its **rich runs flattened**, chip labels included (empty → the editor's placeholder), else
3. the action fragment stream → `describeStoryBlock` + the quick-param tokens.

`storyRowSentence` joins fragments with a single space, matching the flex gap the eye reads there.

### The two coupling points

**(a) `Character[]`.** `describeBlock` used only `profile.getId()/getName()/getColor()`, so the
dependency became `StoryRowLookups.character`, an `id → { name, color? }` table. The workspace builds
one with `characterRowLookup(characters)` (kept in `storySceneBlockUtils`, next to
`isReadableAccentColor`, so the accent still passes the same legibility filter); Dev Mode builds one
from `DevModeCharacterSummary` in `useStoryRowLookups`. `null` vs `{ name: "" }` is preserved — an
unknown id still reads "unknown character", an unnamed one still reads empty, exactly as before.
Nothing from `@/lib/workspace` is reachable from the projection or from dev-mode.

**(b) The asset name.** `DevModeBundle.storyLibrary.assetNames: Record<string, string>` is baked by
`bundleAssembler` from `assets/assets.metadata.{image,audio,video}.json` — the same flat shards the
renderer's asset service owns, reduced to names alone (a broken or missing shard degrades to "no name
for that id", which prints the id, i.e. today's behaviour). The projection takes it as
`lookups.assetName`, following `describeBlockSubject`'s existing shape; with the resolver absent a row
still prints the raw id, so the editor's list and clipboard are untouched.

### Where it lives, and the two back-imports (honest note)

The module is under `src/renderer/lib/story/`, but it imports three pure things from the story editor:
`getCommandGroup` (the command taxonomy — the colour unit the card named), and `segmentToRuns` /
`resolveInterpolationName` (the one description of what an inline chip reads as). They are data and
pure functions, nothing renders, and duplicating either would recreate exactly the drift this card
exists to remove. `lib → apps` imports are the existing house pattern (88 of them on develop), but it
is a smell and I am flagging it rather than hiding it: the tidy version moves the taxonomy and the
rich-run model to `lib/story` too, which is a bigger, mechanical follow-up.

## 3. WI-2: two of the four questions had no data behind them

The card's §1 WI-2 says the round comes from `getStackSnapshot().root.loop` and the parallel's
occupants from `StackFrameSnapshot.branches`. **Both are empty in the running app**, and I only found
that by driving the fixture and dumping the raw snapshot — the first implementation passed its unit
tests and rendered `Repeat` with no round and `1 None  2 None` for the branches.

Measured, from the live instance, walking my fixture (`__U4_STACK` probe in a throwaway tree):

```
in the repeat body : loops: []   root.frames: [{actionId:"studio:…", actionType:"control:all",
                                                branchWaitType:"all", branches:[[]]}]
in the parallel    : loops: []   root.frames: [{actionId:"a-7", actionType:"menu:action",
                                                branchWaitType:"all", branches:[[],[]]}]
```

Confirmed against the engine source (`node_modules/narraleaf-react/dist/main.js`), so this is a
contract fact, not a timing fluke:

- `ControlAction.repeat` returns `wait: { type:"all", stackModels:[createCountLoop(...)] }` — the loop
  is a **nested** StackModel;
- `StackModel.snapshot()` does `r.branches = i.wait.stackModels.map(s => s.snapshot().frames)` —
  it keeps the nested stack's **frames** and drops its `loop` (and `tag`);
- the root stack is `$root`, never a loop. So `root.loop` is empty for **every** `/repeat` an author
  can write in a scene, and `async` only holds `doAsync`/`allAsync` stacks.
- a branch's `frames` are its *pending* items, so a branch waiting on the player is empty — which is
  every moment anyone is reading this panel. Hence `[[]]` / `[[],[]]`.

This also revises §5's reading of the old tab: "轮次一个字都没有" was **not** a UI failure — the old
`StackColumn` did render `stack.loop` when present. The data was never there.

**What I shipped instead** (`ec25fb3b`): the two answers come from the document, where they exist.

- a repeat rung shows the rounds it is **authored** for, `Repeat ×3`, from `getContainerHeaderInfo().repeatTimes`;
- a parallel lists its **own children** as branches, each by the first row that actually says
  something (containers are walked through, so a branch reads `Parallel branch A.` and not `In order`),
  with the branch holding the play head marked `▸`;
- the engine readings are kept and **preferred** where they resolve, so the day `snapshot()` reports
  nested stacks whole this becomes the live `2/3` with no further change here.

**So A-9 as written (`n/3`) cannot pass without an engine change.** It needs
`StackModel.snapshot()` to carry nested stacks whole (`{frames, tag, loop}`) rather than just their
frames. That is an engine card; I did not open one. Everything else in WI-2 is answered.

## 4. WI-3: how the graph got readable

`SceneFlowCanvas` gained two optional props, **both unset in the workspace tab**:
`fitPadding` (default `0.2`, unchanged) and `minTitleRenderedPx`. When the second is set the canvas
reads the live viewport zoom (`useStore(s => s.transform[2])`) and publishes
`--nl-scene-flow-type-scale = clamp(1, min/(12·zoom), 1.6)`; `SceneFlowNode` sizes its title and meta
line through that var with `text-xs` / `text-2xs`'s own numbers as fallbacks, so with the var unset
every computed value is byte-identical to before. The cap is 1.6 because title + meta line boxes are
`16px·scale` each inside a 72px node with 16px of padding.

Dev Mode passes `minTitleRenderedPx: 11.5` and `fitPadding: 0.06`. Measured on the final build:

| | zoom | title CSS px | **effective** | all nodes in pane |
|---|---|---|---|---|
| Dev Mode, before (card §0.1) | 0.600 | 12 | **7.2** | yes |
| Dev Mode, after | 0.6799 | 16.91 | **11.5** | 4/4 yes |

Workspace story-flow tab, after: node CSS font `[16, 16, 16, 16]`, title `12px` / line-height `16px`,
meta `11px`, `--nl-scene-flow-type-scale` unset. Unchanged.

I did **not** raise `minZoom`: at a legible zoom the whole graph does not fit a 380px panel, and a map
with nodes off the edge is worse than a small one.

## 7. Things I could not do, or am unsure about

1. **The live loop round (`n/3`) is not implementable in Studio.** §3. Needs an engine change to
   `StackModel.snapshot()`. The rung shows the authored `×3` instead.
2. **The menu / option container chain has still never been driven.** The card already records that a
   synthesized click does not select a choice option; that has not changed, so `Menu > Option > …`
   was only ever read from the document by unit test, never seen live. It is in my fixture for a human.
3. **Container rows differ from the editor by the repeat count.** The editor's repeat header renders
   its count in an `<input value>`, which is invisible to `innerText` — the editor row reads
   `Repeat times`, the timeline reads `Repeat 3 times`. I judged including the number better for a
   read-only list. If §4 ever extends A-1 to a container scene, this is the one row that will differ.
4. **An empty text row shows the editor's placeholder verbatim** — e.g. `Double-click to enter
   narration` — because that is literally what the editor line says. In a debug panel it reads as an
   instruction to nobody. One projection says keep it; U5's "no explanatory text" says cut it. I kept
   it and am flagging it rather than quietly diverging.
5. **`displayable/transform` rows still differ.** The editor's `DisplayableTransformPreview` prints
   `Transform <name> · <asset>` when the target resolves to an image; the projection prints
   `describeStoryBlock`'s `<operation> <label>`. Not in WI-1's listed coverage, no such row in
   `First Day`, so I left it. It is the last known editor/timeline divergence I am aware of.
6. **The timeline's category bar ignores dialogue-group membership.** The editor also drops the bar on
   an in-group `expression` continuation row; the timeline has no groups, so it shows the hue. Rows
   the editor *does* bar are identical in both.
7. **The parallel's `▸` follows the play head, not the stage.** In the fixture the stage still displays
   branch A's line while the play head has moved into branch B, so the panel marks B. That is the same
   play head the timeline's `▶` uses; it is consistent, but it can look off next to the stage.
8. **The Scenes type scale is capped at 1.6.** With enough scenes to push the fit below zoom ≈0.6, the
   effective title size falls under 11px again. Measured 11.5px at the fixture's four nodes.
