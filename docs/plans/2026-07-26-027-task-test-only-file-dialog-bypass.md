# 文件对话框的测试通道（仅开发模式 + 调试端口）

**授权（用户 2026-07-26）**：允许从调试协议侧加一条绕过原生文件对话框的通道，
**必须严格门控——仅 Studio 开发模式、且调试端口已开启时可用。**

## 0. 为什么要它

「导入 20 个文件全程有进度且失败可重试」是 U3b 的判据之一，**从 U3b 到现在没有任何人验过**，
原因不是没人愿意，是够不到：导入走的是主进程的原生 `dialog.showOpenDialog`，
渲染层的 bridge 是 frozen 的 non-configurable `window` 属性（打不了桩），
而 dev 构建又不是已安装应用（挂不上 UI 自动化）。交接文档 §8.2 记的就是这道坎。

**同时记一条教训**：上一轮有人给这个对话框打桩绕过时，**桩自己造出了一个假缺陷**
（交接文档 §6 第 10 条）。所以这条通道的第一要求不是"能用"，是**"用它得到的结论必须为真"**。

## 1. 门控（这一节是本卡的重点，不是附注）

三个条件**同时**成立才启用，任意一个不成立就当这条通道不存在：

1. 进程是**开发模式**（不是打包后的应用）；
2. **调试端口已开启**（即 `--cdp` / `--cdp-port` 那条路径已经生效）；
3. 一个**显式开关**（环境变量或 CLI flag），默认关。

补充要求：

- 打包产物里**不应包含**这条通道的实现（能 tree-shake 掉最好；做不到也要保证运行期三条门全关）。
- 启用时要在主进程日志里**留一行明确的记录**，让任何看日志的人知道"这次导入没走对话框"。
- 通道只负责**提供路径列表**，不许绕过其后的任何一步：权限授予、扩展名过滤、
  `expandImportPaths`、`importFromPaths` 的 1:1 语义（VoicePanel 按下标配对，见 [[asset-directory-drop-import]]）
  全部照常执行。**绕过的是"人去点对话框"，不是"程序去处理文件"。**

## 2. 范围

- 主进程侧：在 `dialog.showOpenDialog` 的调用点前加一层，门控通过时返回注入的路径列表。
- 一条从调试侧注入路径列表的入口（怎么注入由执行者定：CDP 可求值的挂载点、
  一个 dev-only IPC、或读一个环境变量指定的清单文件都可以）。
- **一个自证测试**：证明三条门任意一条不成立时，通道确实不生效。

## 3. 明确不做

- 不改导入本身的任何行为（进度、重试、失败项的语义都不动——它们正是要被验的对象）。
- 不给拖拽导入加通道（拖拽已经能驱动，见 [[html5-drag-requires-opt-in]]）。
- 不为保存/导出对话框加通道（本卡只解一个具体的验收阻塞）。

## 4. 判据（orchestrator 所有，出卡时补齐并改前标定）

- **门控**：三条门各关一条，通道均不生效（三个负例都要跑，不是只跑正例）。
- **不失真**：经通道导入 20 个文件的结果，与人手选同样 20 个文件的结果**逐项相同**
  （资产 id 之外的一切：数量、名字、分组、hash）。这一条是为了防上一轮那个"桩造出假缺陷"。
  人手那一半需要用户配合跑一次。
- **解锁的目标**：导入 20 个文件全程有进度；构造一个失败项，它可重试且重试成功。
  ——这条才是这张卡存在的理由，U3b 欠着的那条。
- 打包产物里通道不可达。

## 5. 交付

分支 `feat/dev-only-file-dialog-bypass`，不要自己合并。
报告写到 `docs/plans/reports/`，**必须包含三条门的负例证据**；报告里不要写"验收通过"。
