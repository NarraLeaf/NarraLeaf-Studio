# 文件对话框的测试通道（仅开发模式 + 调试端口）

**授权（用户 2026-07-26）**：允许从调试协议侧加一条绕过原生文件对话框的通道，
**必须严格门控——仅 Studio 开发模式、且调试端口已开启时可用。**

## 0. 为什么要它

「导入 20 个文件全程有进度且失败可重试」是 U3b 的判据之一，**从 U3b 到现在没有任何人验过**，
原因不是没人愿意，是够不到：导入走的是主进程的原生 `dialog.showOpenDialog`，
渲染层的 bridge 是 frozen 的 non-configurable `window` 属性（打不了桩），
而 dev 构建又不是已安装应用（挂不上 UI 自动化）。交接文档 §8.2 记的就是这道坎。

**同时记一条教训**：上一轮有人给这个对话框打桩绕过时，**桩自己造出了一个假缺陷**
（交接文档 §6 第 10 条）。所以这条通道的第一要求不是"能用"，是**"用它得到的结论必须为真"**。

## 1. 门控（这一节是本卡的重点，不是附注）

三个条件**同时**成立才启用，任意一个不成立就当这条通道不存在：

1. 进程是**开发模式**（不是打包后的应用）；
2. **调试端口已开启**（即 `--cdp` / `--cdp-port` 那条路径已经生效）；
3. 一个**显式开关**（环境变量或 CLI flag），默认关。

补充要求：

- 打包产物里**不应包含**这条通道的实现（能 tree-shake 掉最好；做不到也要保证运行期三条门全关）。
- 启用时要在主进程日志里**留一行明确的记录**，让任何看日志的人知道"这次导入没走对话框"。
- 通道只负责**提供路径列表**，不许绕过其后的任何一步：权限授予、扩展名过滤、
  `expandImportPaths`、`importFromPaths` 的 1:1 语义（VoicePanel 按下标配对，见 [[asset-directory-drop-import]]）
  全部照常执行。**绕过的是"人去点对话框"，不是"程序去处理文件"。**

## 2. 范围

- 主进程侧：在 `dialog.showOpenDialog` 的调用点前加一层，门控通过时返回注入的路径列表。
- 一条从调试侧注入路径列表的入口（怎么注入由执行者定：CDP 可求值的挂载点、
  一个 dev-only IPC、或读一个环境变量指定的清单文件都可以）。
- **一个自证测试**：证明三条门任意一条不成立时，通道确实不生效。

## 3. 明确不做

- 不改导入本身的任何行为（进度、重试、失败项的语义都不动——它们正是要被验的对象）。
- 不给拖拽导入加通道（拖拽已经能驱动，见 [[html5-drag-requires-opt-in]]）。
- 不为保存/导出对话框加通道（本卡只解一个具体的验收阻塞）。

## 4. 判据（orchestrator 所有；**草案，待改前标定**）

> 标定尚未做。定稿前这一节可能被改写——本仓四张卡的经验是每次标定都会改写判据，
> 而且到目前为止**每一次都是判据错、实现没错**。

### 4.1 注入接口契约（这是接口约定，验收脚本按它写）

- **显式开关 = 环境变量 `NLS_DEV_FILE_DIALOG_BYPASS`**，值是一个 JSON 清单文件的绝对路径。
  变量不存在即"关"（默认关，满足 §1 第 3 条）。
- 清单形如 `{ "selectFile": ["<abs>", ...], "selectDirectory": [...] }`，
  主进程在门控通过时**每次调用都重新读盘**（验收要在两次导入之间改写它）。
- 主进程每次真的绕过对话框时，**日志留一行**，含被绕过的调用点与注入的路径数。
- 启动时**无条件**留一行说明通道状态：armed，或者 disarmed **并写明是哪条门没过**。
  三条门的负例就靠这行 + 下面的 OS 级证据判定。

命中的调用点：资产导入走 `useAssetActions.ts:355` 的 `fs.selectFile` →
`FsSelectFileHandler`（`src/main/.../handlers/fsAction.ts`）。

### 4.2 门控负例（G-*，三条门各关一条，都要真跑）

| id | 判据 | 怎么测 |
|---|---|---|
| G-1 | 打包态不生效 | 单测：门控谓词在 `app.isPackaged === true` 时为 false |
| G-2 | 调试端口没开则不生效 | **不带** `--cdp` 启动 + 环境变量已设 + 清单有效 → 启动日志报 disarmed（原因=无调试端口）；再用桌面自动化点导入，**OS 层枚举到原生文件对话框窗口**（证明没被绕过），然后取消 |
| G-3 | 开关没开则不生效 | 带 `--cdp` 启动、**不设**环境变量 → 启动日志报 disarmed（原因=开关未开）；经 CDP 点导入，同样在 OS 层枚举到原生对话框，然后取消 |
| P-1 | 打包产物里通道不可达 | 生产构建产物中 grep 不到通道实现的标记串 |

**负例不能只看日志。** 日志是实现自己说的话；OS 层真的弹出了原生对话框，才是"通道没生效"的证据。
这一条正是交接文档 §4 那次教训的形状：那次就是**在 OS 层枚举窗口**才看见被吞掉的模态对话框。

### 4.3 不失真（F-1，这张卡的防伪判据）

经通道导入 20 个文件，与**人手/桌面自动化经真实对话框**选同样 20 个文件，
两次结果**逐项相同**：数量、每项的名字、分组、hash（资产 id 除外）。

上一轮给这个对话框打桩时**桩自己造出过一个假缺陷**，所以这条不是形式主义：
通道的第一要求不是"能用"，是"用它得到的结论为真"。

### 4.4 解锁的目标（U-*，U3b 欠着的那条，这才是本卡存在的理由）

| id | 判据 |
|---|---|
| U-1 | 20 个文件导入全程有进度：`n / 20` 至少出现 **3 个不同的中间值**，单调不减，终值 20/20 |
| U-2 | 构造一个失败项：注入的 20 条里有一条是**扩展名合法但文件不存在**的路径 → 条带只列这一项失败并给出 Retry；随后**把那个文件创建出来**，点 Retry → 失败清空、资产数 +1 |

U-2 的失败构造之所以确定可复现：`importFromPaths` 是严格 1:1 顺序循环，
逐条 `importLocalAsset`，读不到就是这一条失败，不影响其余 19 条。

而 G-* 的观测手段（启动日志行、OS 级窗口枚举）在改前就能跑出确定结果。
