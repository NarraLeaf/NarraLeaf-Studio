## 1. 风格铁律

- 复用既有组件。**UI 里不要解释性文本**。不新增依赖、不引入新配色、不加 chip/徽章/图例堆砌。
- 编辑面上不要 `title` 原生 tooltip。
- 发现"要不要加个提示告诉用户…"的冲动时，答案是**不加**。

## 2. 为什么这张卡存在（实测，别当背景读，这是验收的锚）

orchestrator 在 develop 上量过：

- **组内成员行的归属线索是 `1px rgba(255,255,255,0.1)`，对比度 ≈1.1:1**，WCAG 非文本下限是 3:1。
  它在物理上看不见，且**只有 hover/active 时**才变成 `rgba(64,168,196,0.4)`。
- 后果：demo3 `First Day` 里第 7 行 `Hello`、第 8 行 `I am Youki`（都是 YouKi 的后续台词）
  与第 10 行 `The journey is about to begin.`（旁白）**渲染完全相同**。
  分组之后作者反而分不清谁在说话——**分组让信息变少了**。
- 行类别色条 `2px opacity .55` ≈1.6:1，同样低于 3:1。
- 头像容器 24px，占编辑器宽度 1.7%；差分头像/裁剪选区做过的全部工作在这个尺寸下不可见。

### 2.1 改前基线（orchestrator 亲测，develop `a1278e70`，demo3 `First Day`，壁纸开启，`editor.surfaceOpacity` 100，背板 `rgb(11,13,18)`）

| 元素 | 实测值 | 有效对比度 | 目标 |
|---|---|---|---|
| 组内归属导轨（第 7、8 行，静息态、鼠标移开） | `1px rgba(255,255,255,0.1)` | **1.27 : 1** | ≥ 3 : 1 |
| 行类别色条（第 2、12 行） | `2px`，`opacity .55` | **2.87 : 1** | ≥ 3 : 1 |
| 头像容器 | `24 × 24px` | — | compact ≥28、comfortable ≥40 |
| `compact` 行高 / 一屏行数 | `36px` / **20 行**（视口 748px） | — | 一屏行数不得低于 20 |

对比度按"前景按自身 alpha 合成到背板后再与背板比"计算，即眼睛实际拿到的值。
改后我会用同一套方法在 `surfaceOpacity` 100 与 45 两档下复量。

## 3. 与已落地的三档密度和解（orchestrator 裁决，不要另起炉灶）

develop 的 `83fea6f1` 已落三档 `compact | standard | comfortable`
（`STORY_DENSITY_METRICS`：rowBox 28/32/38 + fontScale 1/1.08/1.15）。它们**只是排版刻度、无结构差异**，
所以用户批评的"密度模式意义不明"在三档下依然成立。

**本卡不加第四档、不删档、不改 compact/standard 的数值。** 只做一件事：
把 `comfortable` 从"字大一点"升级成**结构不同的对话块布局**。

## 4. 工作项

### WI-1 归属可见化（三档共用，最高优先，先做）

- 组内成员行的归属线索对比度 **≥3:1**，且**静态可见**（不依赖 hover/active）。
  形状自定（加宽导轨、可见左缘条、缩进+可辨识线索都行），但**不要发明新配色**——用既有 token。
- 行类别色条同样提到 **≥3:1**。
- 头像容器 `compact` 下 **≥28px**（现 24px）。
- **在同说话人连续行里头像只出现一次**的既有行为保持。
- 注意与 `815ac53c`（名牌滚出视野时提示说话人）**不要重复表达**——那是滚动态的补偿，本条是静态归属，
  两者叠加不得出现两个说话人指示。

### WI-1b 左边缘对齐（用户 2026-07-25 观察，orchestrator 实测坐实，三档共用）

用户在执行者的测试夹具上看出两条，我读只读量证实，且比描述更糟。**当前一屏有五条不同的左边缘：**

| 行类 | 文本左边缘 |
|---|---|
| 旁白 | **428** |
| 组内后续对白 | **432** |
| 名牌本身 | 436 |
| 表情行 | 454 |
| 组头对白文本（名牌之后） | **488**（YouKi）／**499**（Nattou） |

- **① 同一说话人的一段话不共享左边缘**：组头 488、后续 432，差 56px。更糟的是组头的文本边缘
  **随名字长度浮动**——Nattou（6 字符）比 YouKi（5 字符）多推 11px。所以不是"一处没对齐"，
  是**每个说话人各有一条边缘**。
- **② 旁白与对白只差 4px**（428 vs 432），这不是区分，是巧合。

**裁决（用户 2026-07-25，覆盖 orchestrator 先前"移动对白以区分旁白"的说法）：**

> 统一左边缘时，尽量让**旁白、人物对话和名字**的左边缘**对齐**，用作文本视觉层级。

也就是说：**一条文本基线**。旁白正文、对白正文、说话人名字**全部**从同一个 x 开始。
区分靠**缩进以外**的手段——字重、字色、角色色、头像、类别条——而不是靠水平位移。

推论（执行者必须满足，形状自定）：
- **名牌不能再行内前置**——行内前置必然把正文推开，且推开的量随名字长度浮动。
  名字要么另起一行作为该段的头，要么进块头；不论哪种，**名字自己的左边缘也落在这条基线上**。
- **头像、导轨、类别色条、行号、把手一律活在基线左侧的固定沟槽里**，不参与正文排布。
- 沟槽宽度**固定**，不随说话人、名字长度、密度档内容变化。
- 表情行（`happy` 现在在 454）同样归到这条基线或明确属于沟槽，不再自成一档。

**判据（orchestrator 用同一套测量复验）**：
- 旁白正文、对白正文、说话人名字**量出同一个 x**（三档各验一次）；
- 该 x **跨说话人相同**（YouKi 与 Nattou 必须一致）；
- 报告里列出每档下**全部不同的左边缘**并逐条说明它承载什么意义——
  理想结果是"一条正文基线 + 一条沟槽边缘"，多出来的每一条都要给出理由。

### WI-2 行号与把手让位（三档共用）

- 常驻的行号 + 拖拽把手列收窄；把手 **hover 才出现**；行号弱化但保留（行号是编译诊断与跳转的锚，不能删）。
- 释放出的横向空间给内容，不要拿去放新东西。

### WI-3 `comfortable` = 对话块

- 连续同说话人 = 一个**块**：左侧一列头像（**≥40px**）+ 角色色名字，右侧多行台词；块内不重复头像与名牌。
- 同角色的 `/face`（`character/expression`）行渲染为块内弱化标注（差分名 + 小头像），**不打断块**。
- **允许改 grid 结构**——上一轮"三列不动"的约束**作废**。
- **但行机械必须逐条保住**：行号连续性、单击选行、双击/Enter 进编辑、跨行拖选、拖拽重排、
  `Enter` 继承说话人、`Escape` 阶梯、右键菜单、RowActions、语音指示、播放头高亮、
  从此行播放。**在报告里逐条自验打勾。**

## 5. 硬约束（踩了就是退回）

- **行列表已虚拟化**（`3e1d3ac8`）。改行高/行结构必然与 windowing 交互：
  测量、滚动锚点、跳转定位都要复验。**长文档滚动不得出现跳动或空白**。
- **不改故事文档 schema**、不改编译器行为、不改投影的语义（分组规则不动）。
- 不动资产面板（U3）、不动 Dev Mode 时间线（U4）、不动检查器跟随选中（U2）。
- 不动 `editor.surfaceOpacity`（U0.1 刚落）。
- 不做位图预烘焙、不引入运行时名牌色。

## 6. 判据（orchestrator 亲验，全部在**壁纸开启**态下）

1. **归属**：demo3 `First Day`，三档各截一张，**不看头像就能判断第 7、8 行属于 YouKi**
   （对照：第 10 行是旁白，必须读起来不同）。
2. **对比度**：组内归属线索与类别色条 **≥3:1**，在 `editor.surfaceOpacity` **100 与 45 两档下各量一次**。
3. **尺寸**：`compact` 头像容器 ≥28px；`comfortable` ≥40px。
4. **密度**：`compact` 一屏可读对白行数**不低于现状**（改前基线由 orchestrator 先量）。
5. **切档无损**：切换密度不丢选择、不丢滚动位置、**文档零变更**（切前切后 storydoc.json 逐字节相同）。
6. **机械等价**：同一行在三档下右键菜单/拖拽/Enter/播放头高亮行为一致。
7. **虚拟化**：500+ 行场景快速滚动无跳动、无空白、跳转定位正确。
